## 第一部分：串口入门

### 1.1 串口到底是什么

"串口"是一种**最简单的两根线通信方式**。一根 TX（发送）一根 RX（接收），加一根 GND（共地参考），三根线两块板子就能聊天。

```
板子 A                 板子 B
  TX ─────────────→  RX
  RX ←─────────────  TX
  GND ────────────── GND
```

**TX 接 RX，RX 接 TX**（要交叉），GND 共地。如果不交叉，就是自己说自己听不到，没意义。

"串"是指 bit 一个一个排队走 —— 不像并口一次八根线一起出去。所以串口慢，但**线少、便宜、抗干扰好**，几乎所有 MCU 都自带几个串口外设。

### 1.2 UART 又是什么

**UART = Universal Asynchronous Receiver/Transmitter**（通用异步收发器）。

它就是 MCU 里实现"串口"的那块**硬件电路**。你写代码 `HAL_UART_Transmit(&huart1, "fan", 3, ...)` 的时候，MCU 内部 UART 这块硬件电路负责把 `fan` 这三个字节按规定的时序从 TX 引脚一个 bit 一个 bit 地推出去。接收端 UART 把这些电平变化重新组装回字节交给软件。

所以"串口"和"UART"日常说话经常混着用 —— 严格说 UART 是芯片里那块外设的名字，串口是它在外部的两根线。

STM32F103 上你能看到 `USART1` / `USART2` / `USART3`（Universal **Synchronous** Asynchronous —— 多了个同步模式，但平时都当 UART 用），它们是**三个独立的硬件外设**。每个有自己**固定的引脚组合**：

| 外设 | TX | RX |
|---|---|---|
| USART1 | PA9 | PA10 |
| USART2 | PA2 | PA3 |
| USART3 | PB10 | PB11 |

注意：**PA9 不能给 USART2 用**。引脚和外设的对应关系是芯片硬件设计死的，软件改不了（除非用 GPIO 重映射，但那是另一个话题）。

### 1.3 波特率（Baud Rate）

UART 是**异步**的 —— 两根线之间没有时钟线告诉对方"现在该读 bit 了"。所以**双方必须事先约定一个速度**，不然接收方不知道每隔多久去采样一次电平。

这个速度叫"**波特率**"，单位是 bps（bit per second）。常见的有 9600、19200、38400、57600、115200、230400 ...

- **两端必须一致**。一端 115200，另一端 9600 —— **收到的全是乱码**，UART 根本不会报错，它就老老实实按 9600 采样，结果电平变化跟节奏对不上，组装出来的字节是错的。
- 速度越快越容易出错，但如果走线短、用低速（比如 9600）几乎不会错，用 115200 在板子内部互联也很稳。

**波特率为什么是异常的数字**（115200 而不是 100000）？因为 UART 时钟分频的关系，这些值能被 MCU 主时钟整除得到的误差最小。习惯就好。

### 1.4 串口"开"和"关"的含义

UART 是 MCU 里的一块外设硬件。**开机默认是关的**，你不主动初始化它就跟没这块电路一样。要"开"它需要做几件事：

1. **打开外设时钟**（`__HAL_RCC_USART1_CLK_ENABLE`）—— 给这块电路供电
2. **配 GPIO 复用模式**（让 PA9 这个引脚不再是普通 GPIO，而是听 USART1 的指挥）
3. **设波特率、数据位、停止位、奇偶校验**（UART 协议参数）
4. **如果要用接收中断**，还得配 NVIC（中断控制器）让这个中断真能进 CPU
5. **调用 `HAL_UART_Receive_IT` 启动接收**

少一步它都不工作。CubeMX 工具就是帮你**勾选项目**自动生成这些代码的，但只要有一项没勾就会留下隐蔽的坑（后面 Bug 复盘会讲到一个真实例子）。

### 1.5 电脑上为什么有那么多 COM 口

电脑没有原生串口（古老的 9 针 D-sub COM 口已经基本绝迹）。现在电脑要跟外面的串口设备通信，得通过 **USB 转串口** 的桥接芯片：

| 桥接芯片 | 厂家 | 驱动名称 |
|---|---|---|
| CH340 / CH340K | 沁恒 (WCH，国产) | "USB-SERIAL CH340" |
| CP2102 | Silicon Labs | "Silicon Labs CP210x" |
| FT232 | FTDI | "USB Serial Port" |
| ST-Link 虚拟串口 | ST | "USB 串行设备" |

每个 USB 转串口设备插上电脑会被分配一个 **COM 号**（COM3 / COM17 / COM25 等等），数字是 Windows 按插入顺序随便分的。

你电脑上看到三个 COM 口：

```
COM17  USB-SERIAL CH340     ← 一根 USB-TTL 转接线，挂在 ESP01s 调试串口上
COM23  USB 串行设备          ← ST-Link 调试器自带的虚拟串口
COM25  USB-SERIAL CH340K    ← 天问 ASR-PRO 板上自带的 USB 烧录口
```

**关键概念**：每个 COM 口背后**只通到一对特定的物理线**。COM25 接到天问板子的 USB 口里 → 天问芯片内部有个"调试串口"绑在那个 USB 上 → 你只能看见走那条调试串口的字节。

天问的 PA_2 / PA_3 是芯片**外面的引脚**，跟 USB 口物理上是两条独立的通道。**COM25 看不到 PA_2/PA_3 上跑的字节**，就算两边都是天问芯片也不行。要看 PA_2/PA_3 上的流量，必须**用一根 USB-TTL 线物理夹到那两根引脚上**，电脑才能旁观。

### 1.6 一图看懂"几个串口分别在干什么"

```
                     ┌─────────────────────┐
                     │  STM32F103 (头盔主控) │
                     │                     │
  ESP01s   ──TX──→  PB11 (USART3 RX) ───┐ │
                                          │ │
              ←─RX── PB10 (USART3 TX) ────┘ │
                                            │
              ←─RX── PA10 (USART1 RX)  ─────┐
                                            │
                     PA9  (USART1 TX) ─────┘├───→ 天问 PA_3 (它的串口1 RX)
                                            │
                                            │     天问 PA_5 ──→ 继电器 IN1
                                            │     天问 PA_6 ──→ 继电器 IN2
                                            │
                     PA2  (USART2 -)        │
                     PA3  (USART2 -)        │
                     │                      │
                     │  USART2 经 ST-Link    │ ──→ COM23 (电脑)
                     │  虚拟串口 (调试)      │
                     └─────────────────────┘

  ESP01s 的 TX/RX ──── 一对夹子 ──→ COM17 (电脑串口助手)  [可选监听]

```

每条 USART 的字节流互相不见面，要看哪条就在哪条上挂个监听设备。

### 1.7 数据库不需要打开串口，但下行控制需要

你之前问过的一个好问题：

> 为什么不用打开语音的串口我也能收到识别结果？

因为你之前的项目里，**STM32 → 后端**是**单向上报**：STM32 把传感器数据通过 ESP 发给云端，云端写库。**STM32 这边只发不收**。所以 STM32 的 USART3 RX 中断你没启动也没事 —— 反正你没打算从 ESP 那边收东西。

但**控制继电器**是反方向：**云端 → STM32 → 天问 → 继电器**。这是**下行**。下行链路上每一段的"接收能力"都得**显式打开**：

| 段 | 谁在接收 | 默认状态 | 要做什么 |
|---|---|---|---|
| 网页 → 后端 | Node.js socket | 默认开 | / |
| 后端 → ESP TCP | ESP 内部 TCP 栈 | 默认开 | / |
| ESP 串口 → STM32 USART3 | STM32 的 USART3 RX 中断 | **默认关** | CubeMX 勾上 NVIC + `HAL_UART_Receive_IT` |
| STM32 USART1 → 天问 PA_3 | 天问的串口 1 外设 | **默认关** | 在天问图形编辑器里给串口 1 设波特率 |

**这次 Bug 真凶就是最后这一段没开**。

## 第二部分：Bug 调试复盘

### 2.0 故事开头

需求：网页 dashboard 上有"开风扇 / 关风扇 / 开 LED / 关 LED"四个按钮，点了之后对应继电器要响。

链路（设计意图）：

```
网页按钮
  ↓ WebSocket
Node.js 后端
  ↓ TCP 转发
ESP01s（透传模式）
  ↓ AT+CIPSEND 把网页发的 JSON 透传到串口
STM32 USART3 RX
  ↓ 解析 {"fan":1} 这种 JSON
STM32 USART1 TX
  ↓ 发 "fan" 字符串
天问 PA_3 RX
  ↓ 串口 1 接收回调
天问拉 PA_6 高电平
  ↓
继电器吸合
  ↓
风扇通电
```

听起来很顺。实际上**每一段都出过问题**，而且**真凶藏在最后一段**。

### 2.1 第一次尝试 —— USART3 NVIC 没启用

**症状**：按按钮，继电器毫无反应。dashboard 显示命令到了后端，后端也确实发到 TCP 给 ESP 了。

**当时的猜测**：STM32 USART3 真的收到 ESP 透传过来的字节了吗？

**怎么验证**：在 STM32 这边加诊断回声 —— 一旦 `parse_and_apply_cmd` 真的被调用，就立刻往 ESP 上行一个 `{"_dbg_recv":1}` 之类的特殊 JSON，后端 log 就能看到。

烧好按几次按钮，**后端 log 里始终没有出现 `_dbg_recv`**。说明 `parse_and_apply_cmd` 根本没跑过。再往前推 —— `esp_process_cmd` 里第一行 `if (uart3_rx_index == 0) return;` 直接就 return 了。也就是 **STM32 USART3 的接收缓冲区始终是空的**，从来没收到过字节。

**找根源**：去翻 [Core/Src/usart.c](Core/Src/usart.c) 里 USART3 的 MspInit：

```c
// USART1 那段 —— 有这两行：
HAL_NVIC_SetPriority(USART1_IRQn, 2, 0);
HAL_NVIC_EnableIRQ(USART1_IRQn);

// USART3 那段 —— 这两行不见了
```

CubeMX 生成的代码里 **USART3 的 NVIC 中断从来没被启用过**。这意味着：

- USART3 GPIO 配好了 ✅
- USART3 外设时钟开了 ✅
- 代码里调用了 `HAL_UART_Receive_IT` ✅
- **但 NVIC 这边 USART3 中断没使能** ❌
- → 字节进了 USART3 的硬件接收寄存器，**永远不触发中断**
- → `HAL_UART_RxCpltCallback` 永远不被调用
- → `uart3_rx_buffer` 永远是空的

**修法**：手动在 [Core/Src/usart.c](Core/Src/usart.c) 的 `USART3_MspInit` 加上 NVIC 启用：

```c
HAL_NVIC_SetPriority(USART3_IRQn, 2, 0);
HAL_NVIC_EnableIRQ(USART3_IRQn);
```

并在 [Core/Src/stm32f1xx_it.c](Core/Src/stm32f1xx_it.c) 加上中断处理函数：

```c
extern UART_HandleTypeDef huart3;  // 顶部加 extern

void USART3_IRQHandler(void)
{
  HAL_UART_IRQHandler(&huart3);
}
```

> **小白笔记**：CubeMX 工具里"启用串口"是分两步勾的 —— 一步是 GPIO/外设本身（默认勾了），一步是 **NVIC 中断**（在 NVIC 设置那个 tab 单独勾）。少勾后者就会留下"串口能发不能收（中断模式下）"的隐蔽 Bug。生成的代码看起来一切正常，运行时悄无声息地丢字节。

**结果**：烧录后，按按钮 dashboard 显示有 `_dbg_recv` 出现了 —— STM32 这边的接收链路打通了。**但继电器还是不响**。

### 2.2 真凶现身 —— 天问串口 1 没启动

NVIC 修了之后还是不响，那 STM32 这边还能怎么验证？只剩一种可能：**STM32 USART1 发出去的字节，天问没收**。怎么测？

**绕开所有上层逻辑**，在 STM32 主程序最外面硬编码"开机后过几秒就主动给 USART1 发 `fan`"：

```c
HAL_Delay(5000);
my_printf(&huart1, "fan");
HAL_Delay(2000);
my_printf(&huart1, "fanoff");
```

如果继电器响了 → STM32→天问这段是通的，问题在更前面（ESP→STM32）；如果还是不响 → 问题在天问那边。

**结果**：继电器**完全没反应**，连串口助手挂在 STM32 PA9 上也看不到字节。

这时候让用户回到天问那一侧检查图形程序，发现了真凶 ——

**天问 ASR-PRO 内部其实有两个独立的子系统**：

```
┌──────────────────────────────────────┐
│         天问 ASR-PRO 芯片            │
│                                      │
│   ① 语音识别 DSP（独立硬件）         │
│   开机自启，麦克风一直在听            │
│      ↓                                │
│   ② 用户图形程序                      │
│   "当语音识别 开风扇 时 → 拉 PA_6 高" │
│      ↓                                │
│   PA_5 / PA_6 → 继电器               │
│                                      │
│   ③ 串口 1 外设（PA_2/PA_3）         │
│   默认关，需要手动配波特率才启动      │
│      ↓                                │
│   ② 用户图形程序                      │
│   "当串口 1 收到 fan 时 → 拉 PA_6 高" │
│                                      │
└──────────────────────────────────────┘
```

**① 语音识别**和**③ 串口外设**是两套**完全独立的硬件子系统**。

- 语音识别开机自启 → 所以"嘴说开风扇"一直好使
- 串口外设要在图形程序里**显式给波特率**才会启动 → 之前那栏波特率是 `-`（未配置）→ **整个串口 1 外设根本没上电**

→ STM32 USART1 发出去的字节到了天问 PA_3 引脚那个位置，**但天问的串口 1 外设没工作，等于这个引脚是悬空的**，字节进了天问芯片就消失了。

→ 那条"当串口 1 收到 fan 时"的规则永远不触发，因为它后面的事件源（串口 1 接收）从来没产生过事件。

**修法**：打开天问图形编辑器，把"串口 1 波特率"那个下拉从 `-` 改成 **115200**（要跟 STM32 USART1 的 115200 一致）。然后烧录天问。

**结果**：网页按按钮，继电器响了。**完结**。

### 2.3 顺手补完的另外几条规则

天问图形程序原本只有 `当串口 1 收到 "fan" 时 → PA_6 高`。但 STM32 关风扇时发的是 `fanoff`，没规则匹配 → 继电器关不掉。

补全：

| 收到字符串 | 引脚 | 输出 |
|---|---|---|
| `fan`     | PA_6 | 高电平 |
| `fanoff`  | PA_6 | 低电平 |
| `led`     | PA_5 | 高电平 |
| `ledoff`  | PA_5 | 低电平 |

（如果继电器接线相反，PA_5 和 PA_6 调换。）

### 2.4 排查过程中顺手做的两件事（不是真凶但有用）

这次主线只有两个真凶（NVIC 和天问波特率），但排查过程中观察到两个现象，顺手改了，对项目稳定性有帮助：

**(1) 按按钮时 TCP 偶尔 ECONNRESET**

后端 log 看到：
```
05:02:56 🎮 控制命令 fan on
05:02:56 TCP 错误: read ECONNRESET
```

**原因**：ESP01s 在 AT 模式是半双工，正在 `AT+CIPSEND` 上行的时候撞上 `+IPD` 下行就会撕掉 socket。原来上行 2 秒一次缝隙太小。

**改动**：上行间隔从 2 秒拉到 5 秒，给下行让窗口；同时加 TCP 自愈 —— USART3 收到 `CLOSED`/`SEND FAIL` 关键字就标记 `tcp_dead=1`，下次上报前先 `AT+CIPCLOSE` + `AT+CIPSTART` 重连。

**和真凶的关系**：没有。即使 TCP 不撕，继电器照样不响（因为天问波特率没开）。但这个改动让"按按钮断网"的副作用消失了，UX 更顺。

**(2) 演示用的血氧/心率占位抖动**

血氧没接真传感器时，`dis_spo2 = 0`，dashboard 显示一直是 0 不动，演示效果差。改成 `HAL_GetTick()` 取模生成 96~98 / 73~78 范围的伪抖动数。纯演示，跟 Bug 无关。

### 2.5 为什么 COM25 串口助手什么都看不到

用户多次问过这个问题，关键概念：

天问板子上的 USB 口（被电脑识别成 COM25）**只通到天问内部的"调试串口"**。这个调试串口是**另一个独立外设**，跟 PA_2/PA_3 上的"串口 1"没有任何物理连接。

类比：STM32 上的 USART1（PA9/PA10）和 USART2（PA2/PA3）是两个独立外设，发到 USART1 的字节绝不会出现在 USART2 上。同理，天问的"USB 调试串口"和"串口 1"也是两个独立外设。

要在 COM25 上看到字节，需要在天问的图形程序里**主动写**：

```
[串口 -]  输出  "hello"   ← 这里的 "串口 -" 默认就是 USB 调试串口
```

这种是你**主动 print**才能从 COM25 看到。`PA_2/PA_3` 上别人发来的字节它看不见。

如果你真想用串口助手看 PA_2/PA_3 上跑的字节，方法是：
- 拿一根 USB-TTL 转换线（比如 CH340 那种）
- 把它的 RX 引脚**并联**夹到 STM32 PA9（也就是天问 PA_3）那条线上 —— 注意是并联（多挂一个监听），不是切断
- USB-TTL 的 GND 跟 STM32 / 天问共地
- 串口助手设 115200 / 8 / N / 1
- 这时候你能旁观 STM32 发给天问的所有字节

但这次问题已经解决了，不需要做这个。

## 第三部分：经验教训

### 3.1 调试链路问题的正确顺序

**从最便宜的一端开始验证**。这次链路 7 段，前 6 段都在 STM32 这一侧，能用代码反复改反复烧。最后一段在天问那边，需要打开另一个 IDE，用户操作。结果真凶就在那段。

**正确顺序应该是**：

1. 先确认天问能收能解 —— 拿 USB-TTL 直接喂 `fan` 给天问 PA_3，**继电器响就说明天问那侧 OK**
2. 再确认 STM32 → 天问 —— 在 STM32 主循环里硬编码发 `fan`
3. 再确认 ESP → STM32 USART3 —— 加诊断 echo
4. 最后才是上层逻辑

如果一开始就这么测，几分钟就能发现"天问串口 1 波特率没设"。我们花了几小时才到这一步。

### 3.2 同设备已工作的功能 ≠ 相邻功能也工作

天问"语音识别"工作完美 → 一开始默认它"是好的板子"。结果**串口和语音是两套独立硬件**，语音工作不能证明串口工作。

**任何"通"的判断都必须用**那条具体路径**测**，不能用"差不多的路径也通"作为依据。

### 3.3 默认关的外设是常见隐患

很多 MCU/SOC 的外设**开机默认是关的**：

- STM32 的 USART：要打开时钟、配 GPIO、配波特率、配 NVIC 才能用
- 天问的串口 1：要在图形程序里给波特率才会启动
- ESP01s 的 TCP：要 `AT+CIPSTART` 才建连接

**写代码时一个忘配，硬件就静默罢工**，没有报错。这是嵌入式调试最常见的坑之一。

养成习惯：怀疑某个外设没工作时，**先确认它真的被启动了**（看初始化代码、看寄存器、看时钟）。

### 3.4 半双工设备小心节奏

ESP01s AT 模式半双工 —— 上行 `AT+CIPSEND` 跟下行 `+IPD` 撞车就断 socket。

如果要做高频双向通信：
- 降低上行频率给下行让路（这次用的方案）
- 改用 MQTT（ESP 内部能更好处理）
- 改用透传模式（`AT+CIPMODE=1`）后就是纯字节流，但失去 AT 命令能力
- 用 ESP IDF 自己写应用层，最灵活

### 3.5 加诊断输出的两难

我们加 `_dbg_recv` echo 的时候，**它本身也是一次上行**，反而加重了节奏冲撞。

调试时加 print/echo 是好习惯，但**要意识到 print 本身可能是新的副作用源**。如果担心，可以：
- 让 print 只在第一次触发时输出（避免反复刷屏）
- 用 GPIO 翻转代替 print（拨个 LED 而不是发字节）
- print 用单独一条不冲突的链路（比如 SWD ITM）

## 一句话总结

**继电器不响**有两个真凶：

1. **STM32 USART3 NVIC 没在 CubeMX 里启用** —— ESP 透传过来的下行字节进了硬件寄存器但永远不触发中断，软件层"以为没收到"
2. **天问 ASR-PRO 串口 1 波特率没配** —— 一个图形编辑器里的下拉框，决定了串口外设有没有上电。语音识别和串口是天问内部两套独立硬件，语音工作不能证明串口工作
